## Coding Principles

优先只保留一条真实的代码路径。代码库、已有依赖或标准库已经实现的功能直接复用，并照仓库在同类场景里的现有写法来做，不要手写一个功能重复的 parser、matcher 或 helper。要提高可读性，就改命名、类型和控制流；如果一个 helper、wrapper 或抽象唯一的作用是让实现看起来不言自明，就不要加。值按它标识的东西命名，操作按它保证的结果命名。给新文件、目录、标识符或 key 起名前，先看仓库里同类东西的现有名字，大小写、分隔符、词序和前缀都照着来。仓库或所用的库没有用过的缩写不要引入，只重复所在目录、模块或命名空间的前缀或路径段也不要加。env var、配置开关、缓存、fallback、兼容层或抽象，只有现有调用方、部署环境、迁移路径或有文档的外部 API 行为需要时才加。

改动的每一行都要落在根因、直接依赖它的地方，或下面说的顺手修复之内。自己的改动造成的无用代码要清掉，比如不再被用到的 import、变量，以及变得不可达的函数。用户纠正或 review 指出的一处问题代表一类问题：在任务负责的范围内找一遍，包括交给 subagent 的工作和给它写的说明，确认属于同一类的都修掉，不管是谁引入的。实现过程中碰到已确认的缺陷，如果修复在任务能改的范围内，成本低、风险低、能验证，也不需要只有用户或其他负责人才能做的决定，就一并修掉，但不要夹带无关的重构。报告「发现了但没修」时，要写出它不满足哪个条件，比如属于其他负责人，或者修复成本明显高于它造成的问题；「任务开始前就有」或「不在改动的文件里」不算。这类缺陷挡住修复时，列出选项和各自的影响，问用户一次，用户决定后不再问。代码库里两种写法互相矛盾时，不要混用：选一种（更新的或测试更充分的），说明理由，并指出另一种。

修改配置常量、业务阈值或风险参数前，先找到读取它的地方，并说明调整方向的效果，例如 `larger = more aggressive`。

做增量的前端改动时，保留现有的 design token、组件和响应式行为，不加没要求的功能或装饰性 UI。打开运行中的 URL 或文件预览检查 UI；只有不占用正在使用的实例的资源时，才自己启动应用。没有检查渲染出的 UI，就在最终回答里说明。

每个测试保护一个独立的行为分区、回归或交互约定，断言从这个约定推出来。有效的断言能拒绝一个合理的违反，又不会在行为不变的改动上失败。输入分区、生产代码路径、观察内容和失败方式都相同的测试不要重复写。可复现的 bug，已有的回归检查能覆盖时就用它。新加回归检查时，先确认它会拒绝有问题的行为，再用它通过来证明修复有效。保留仓库要求的检查，没验证到的重要行为要报告出来。

让代码自己说明它做了什么。注释写在负责这件事的边界上，说明不明显的原因；只有维护者需要据此判断理由何时失效时，才写约束或失效条件。注释不复述操作，不保留中间尝试过的做法，不列猜测的未来工作；长期有效的约定写进负责它的文档。注释和普通项目文档只写当前状态。改写已有的句子时，按当前状态从头写，不要在旧句子上改。每个细节都要是不知道这次改动的读者理解或使用当前配置时需要的：不拿现在的行为和被替换的做法对比，也不单独提出或强调只因为这次改动碰过的内容。不写由别处维护、会被改掉的具体值，例如模型名、版本号、数量、日期，除非这段文字就是定义这个值的地方。改动的原因和经过写进 commit message。有 PRD、todo、changelog 这类项目文档时，让它们和实际改动保持一致；计划只列工作项，不写时间估计。
