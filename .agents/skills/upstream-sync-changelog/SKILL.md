# 上游同步与学习日志

只服务于当前 chezmoi 仓库。目标不是复述 diff，而是让用户理解上游改变了什么、为什么、如何使用、能学到什么，以及哪些内容在本地继承、覆盖或未跟踪。

正常调用执行「更新上游缓存 → 固定版本 → 运行同步脚本 → 清理已确认的上游删除项 → 分析 → 保存增量报告」。用户明确只要求解释或审阅时，遵守只读范围，不执行复制或删除、不推进 changelog 基线。同步不包含 `chezmoi apply`、安装、修改本地覆盖或同步清单、提交及推送。

## 1. 确定上游基线和执行前状态

读取本仓库 `AGENTS.md`、`.github/scripts/sync-upstream.paths`、`sync-upstream.sh` 和 `.github/docs/upstream_changelog/` 中已有的报告。

- **上游基线**：首次使用 `4ac6515fa`，取得历史后解析为完整 commit hash；后续使用上一份完整报告的 `upstream_head`。不能用本地 `HEAD`、提交日期或当前 `main` 代替。
- **清单变化**：以执行开始时 `.github/scripts/sync-upstream.paths` 的 Git diff 为准，分别读取 `git diff --cached -- .github/scripts/sync-upstream.paths` 和 `git diff -- .github/scripts/sync-upstream.paths`。两者均为空则无需在报告中说明；有影响跟踪范围或消费者的差异时，在相关主题中解释当前未提交的规则变化。不与上一份报告比较，不保存清单原文或快照元数据。
- 按报告的 `previous_report` 关系查找唯一的最新完整记录，不按文件修改时间猜测。报告链分叉、引用缺失、上游版本元数据不一致时，停止确认；未完成的草稿不能充当基线。

分别记录本地 `HEAD`、暂存、未暂存及未跟踪状态，供运行后判断本次新增的 unstaged diff；新复制但尚未跟踪的文件也计入实际变化。清单变化及既有本地差异不能算作本次同步产生的差异。取得固定上游快照后，再按脚本规则检查实际覆盖范围。

## 2. 在固定目录取得上游历史

固定使用 `/tmp/chezmoi-upstream-sync-report/`，其中 `liby-dotfiles/` 是持久复用的上游 clone；每次运行的日志、前后快照和脚本缓存放在该目录下独立的运行子目录。

先对这个共享目录取得原子目录锁，重新核对第 1 节的报告基线，持锁直到本次报告保存或停止。已有锁时停止或等待，不擅自移除；只释放自己取得的锁。

- clone 不存在时，完整 clone `https://github.com/liby/dotfiles.git`，保留提交历史和 tags，不使用浅克隆。
- fetch 前为已有报告的旧上游版本保留本流程专用 ref，避免 force push 后旧对象失去引用；旧对象缺失时，先从本流程持久 clone、既有脚本缓存或远端取回，不删除旧缓存。
- 已存在时，先核对 origin、工作树和浅克隆状态；来源不符或有未知本地改动时停止，不删除重建。确认是本流程的干净缓存后 fetch 上游 `main` 和 tags；历史不完整时补全。
- 将本次目标固定为取得后的 `origin/main` 完整 hash。基线是目标的祖先时，按原区间查看 log、commit message 和 diff；不是祖先时，按下面的历史恢复流程继续，不仅因 force push 暂停。
- 记录**精确指向目标 commit 的上游 Git tags**；没有则为 `[]`。最近祖先上的 tag 不是当前版本标签。

上游历史被 force push 改写时，通过历史 diff 推定新历史中对应的起点：

1. 保留上一份报告的旧 `upstream_head` 作为实际变化基线。取得旧、新历史的共同祖先，对两侧提交序列做 `git range-diff`；用 `git patch-id --stable`、受影响路径及前后源码核对对应关系。完整 tree 相同可证明快照等价；补丁或提交标题相同不能单独证明整份快照等价，也不按时间或短 hash 猜测。
2. 结合旧 head 及相邻提交的对应关系，定位新历史中唯一、证据一致的对应 commit，作为历史讲解的推定起点。检查旧 head 到对应 commit 的端点 diff，识别重写时补入、撤回或改变的内容，再解释对应 commit 到固定新 head 的后续演进。对应关系不唯一时继续核对历史与源码；仍无法判断才询问，不擅自把共同祖先当成新的已同步基线。
3. 实际 A/D/M、跟踪范围筛选与删除候选始终使用 `git diff --no-renames <旧 head> <固定新 head>` 的两个快照端点，即使它们没有祖先关系。不能只比较推定起点到新 head，否则会漏掉重写中修正的旧提交；也不能把所有改 hash 的提交重新算作新增内容。
4. 新报告的 `upstream_base` 仍保存旧 head，`upstream_head` 保存实际同步的新 head，`previous_report` 指向上一份完整报告。在「范围与速览」简述历史改写、推定起点及对应证据，相关主题解释重写带来的实质差异。旧快照无法取回时，不用报告文字或本地混合工作树代替源码，停止同步与报告写入并说明缺失证据。

本地比较范围、上游历史区间和本次同步前后差异是三种证据，分析时保持区分。

## 3. 让分析版本与脚本实际复制版本一致

**上游内容写入仓库只能通过 `.github/scripts/sync-upstream.sh` 执行**；不得手工复制文件、应用上游 patch 或另写复制程序代替它。前态备份和已确认删除项的清理不替代同步脚本。

当前脚本默认使用自己的浅克隆和 TTL 缓存，且 `UPSTREAM_REF` 传给 `git clone --branch`，不能直接把任意 commit hash 当作 branch 使用。不要分析最新 clone，却用默认缓存执行同步。

先按固定上游快照和脚本的源路径、目标路径、目录包含、排除及映射规则列出本次实际复制目标及上游删除项对应的本地目标。删除候选以固定上游区间的 D 状态为依据；若上游 hash 未变，沿用待更新报告的 `upstream_base..upstream_head` 区间，按本次清单对基线源码的有效包含、排除和映射规则解析；不把「目标快照里找不到」单独当作删除证据。遇到目标上的未提交差异或未跟踪文件，先查明来源；除非确认与本次将复制的内容一致、不会覆盖不同状态，否则暂停同步并报告冲突。用户已明确授权覆盖或删除时，按其授权范围继续，不重复询问。不要自动 commit、stash，也不要把上游副本上的本地改造当成应保留的定制。不相关的工作树改动不阻止同步，也不纳入报告。

在上游 clone 中为目标 hash 创建本流程专用分支，例如 `sync-report-<完整 hash>`；同名分支若已存在，必须确认仍指向该 hash。该分支只作不可移动的同步入口，不改写上游 `main`。随后用本地 clone 作源、独立运行缓存调用现有脚本：

```sh
UPSTREAM_REPO="$upstream_dir" \
UPSTREAM_REF="$pinned_ref" \
XDG_CACHE_HOME="$run_dir/cache" \
SYNC_CACHE_TTL_MIN=0 \
zsh -f .github/scripts/sync-upstream.sh > "$run_dir/sync.log" 2>&1
```

其中 `upstream_dir` 是上述固定 clone，`pinned_ref` 是已核验的专用分支，`run_dir` 是本次新建的运行目录；在本仓库根目录执行。`zsh -f` 跳过用户启动文件，避免 `.zshenv` 重设缓存变量；仍需核验脚本实际使用的缓存位置。运行前保存复制、删除目标的前态，并临时记录清单内容标识用于核验运行期间未改变，确保文件变化可恢复，并且不改变用户的 index。

运行后检查退出码、完整日志、脚本实际使用的 clone 的 `HEAD` 和所有复制目标，按脚本真实复制语义与固定上游快照核对。确认清单在运行期间未改变；上游 clone 的当前 `HEAD` 或远端 `main` 不能替代对实际复制来源的核验。

- 脚本只负责复制。复制来源、所有复制目标及清单核验通过后，清理预检确认的上游删除项：核对精确本地路径和可恢复前态，逐个删除并核验结果，保持 index 不变。映射源的本地保留版本、排除项、清单外文件及已部署到 `$HOME` 的文件不在清理范围；清单移除或改映射产生的旧目标也不因本流程自动删除。
- 将复制与删除分别记录在运行目录中，报告分别统计上游 A/D/M、本次复制和本次删除。未知来源、缺少可恢复前态或删除失败的目标保留现场并单列，不称清理完成；若它属于本次应删除的目标，不创建或更新完整报告、不推进基线。
- `missing upstream` 即使伴随退出码 0 也要逐项解释。已由上游删除证据解释的缺项及清理范围之外的遗留文件可以作为明确的同步警告记录，不能因此宣称完整镜像或清理范围外的文件已删除。
- 复制失败、来源不符、目标无法核验或清单中途改变时，保留前态、日志和现场，不创建或更新完整报告、不推进基线；先查清部分执行的结果，不盲目重跑。

后续叙述区分「从上次报告起的上游演进」与「本次脚本复制及删除步骤实际改变的本地文件」；本地此前已同步的变化也可能属于前者。

## 4. 解释变化与学习价值

先用固定上游区间的端点 diff（历史改写时为旧 head 与固定新 head）完整列出上游新增和删除路径，包括清单外的路径；每项解释用途或删除原因，并标注有效跟踪范围、本地新增／删除／不存在／保留状态。为避免改名遗漏，用 `--no-renames` 取得 A/D 清单，叙述时可把对应旧、新路径归为改名；没有新增或删除时明确写无。凭据和加密文件只列路径与状态。

结合本次清单的有效源路径筛选上游变化；若清单有 Git diff，同时核对差异涉及的旧规则，保留停止跟踪的说明；不要拿映射后的本地路径直接过滤上游历史。按主题组织报告，但完整覆盖比较区间内所有已跟踪文件的有效变化。用**前后源码 diff + 相关 commit message + 相邻文档及消费者**建立因果，不把 commit 标题当成实现或生效证据。端点 diff 表示最终变化；值得学习的中间尝试、修正或撤回可单列为演进过程，不说成当前仍存在的能力。

每个实质主题回答：

1. **改变了什么**：原行为、现行为、关键源文件和本地目标路径。
2. **为什么这样改**：解决的问题与上游提交依据；缺少直接依据时明确标注推测。
3. **我怎么用**：触发方式、配置入口、适用场景和前提；给出可理解的例子，但不替用户执行部署或安装。
4. **能学到什么／巧思**：结合具体实现解释机制、取舍和可迁移的做法，不用「提升体验」等空泛评价替代。
5. **本地采用情况**：沿着映射副本、本地覆盖、模板和消费者说明哪些变化原样继承、被覆盖屏蔽或缺少清单外依赖，以及需要用户决定的采用取舍。

机械性改动可合并简述，不为每个文件强行编造学习点。关键源文件、本地目标和采用差异放在相关主题中，不另列文件变化索引。可信上游无需在本任务中重复做语法、解析或运行验证；仅在本地覆盖与上游变化存在具体冲突时做必要的定向检查，不执行带安装或部署副作用的模板、hook 或脚本。

另设「值得引入」：浏览区间内清单外的相关上游变化，最多选 3 项有证据、适合本项目的技术或设计。说明用途、当前清单未覆盖的事实、采用前提及成本；无依据时不编造未跟踪的原因。它们不是已同步或已启用的功能。没有值得推荐的条目就明确写无，不凑数、不自动改清单。

加密文件、凭据和私有值保持不透明，只报告路径、状态与清单归属；不读取、解密、展示内容，也不放进示例或报告附件。无法确认的来源和影响单列，不硬塞进上游结论。

## 5. 检查同步清单的 Git diff

仅当执行开始时清单的暂存或未暂存 diff 改变了跟踪范围、映射、排除或保留关系时，在受影响的主题中说明对目标和消费者的影响。diff 为空或只有注释、格式变化时不写；不单列「同步清单变化」章节，不复述现有跟踪范围，不把已提交的规则当作本次新增。

注意 `!` 匹配的是本地目标，目录规则覆盖子项；`源 > 目标` 同时保留本地源路径。Git diff 中被移除的规则用于解释停止跟踪，不能继续列为本次已同步。新加入的路径要区分上游区间内的变化与本次首次引入的现有内容，不能把后者全部归因于新提交。

## 6. 新建或更新对应版本的报告

每个上游版本在 `.github/docs/upstream_changelog/` 保存一个中文 Markdown 报告，不生成独立 `.paths` 或 `.sync.log` 附件。首次记录或上游 hash 改变时，新建 `YYYYMMDDTHHMMSSZ_<上游短 hash>.md`；文件名时间为 UTC，撞名时另选唯一名称，不覆盖其他版本的报告。

完整日志、前态备份及删除记录只保留在运行目录。报告聚焦上游变化、原因、用法、设计思路和本地采用差异；例行来源核验、语法检查和未执行 apply／安装／启动服务的说明不写入报告。实际同步缺项、删除失败或本地覆盖冲突若影响内容完整性或采用方式，放在相关主题中说明。先完成复制、删除和清单核验，再新建或更新完整报告。

上游 hash 与最新完整报告的 `upstream_head` 相同时，完成同步后检查新的 unstaged diff：对比运行前后的未暂存状态，结合本次实际复制、删除目标及新文件定位差异；同时检查 `.github/scripts/sync-upstream.paths` 的未暂存 diff 是否改变了跟踪或映射规则。清单变更可能让同一上游版本首次引入、停止跟踪或采用不同目标，但不能被描述为新的上游提交。只处理本次同步相关、且尚未反映在对应报告中的变化；无关本地改动及报告本身的未暂存 diff 不触发更新。

- 有上述变化时，**原位更新该版本已有的最新完整报告**，保持文件名、`upstream_base`、`upstream_head` 和 `previous_report` 不变；更新 `recorded_at`、`local_head`、主题及本地采用情况。分析仍使用该报告原有的上游区间，不把基线改成与 head 相同的空区间。
- 新跟踪的内容归入对应主题，补充用途、设计思路和本地目标；已引入的推荐项移入已跟踪笔记或修正其采用状态。停止跟踪、改映射或删除改变的本地结论同步修正，保留原报告中仍成立的上游学习内容，不追加重复段落。
- 没有新的相关 unstaged diff，且清单没有尚未反映的实际范围变化时，只反馈无增量，不改报告、不新建同 hash 记录。

同 hash 更新写入前备份现有报告，重读确认它仍是锁内确定的对应记录。复制、删除或来源核验失败时，保留原报告与现场，不将部分结果写成完整记录。

报告使用以下 frontmatter；hash 保存完整值，`previous_report` 首次为 `null`，否则指向 changelog 目录中上一份完整报告的文件名。不保存清单快照字段：

```yaml
---
status: complete
recorded_at: "<ISO 8601 UTC 时间>"
upstream_repo: "https://github.com/liby/dotfiles.git"
upstream_ref: "main"
upstream_base: "<完整起点 commit hash>"
upstream_head: "<实际同步的完整 commit hash>"
upstream_tags: []
topics: ["<技术主题标签>"]
local_head: "<同步前的本地完整 HEAD>"
previous_report: null
---
```

`upstream_tags` 只存精确 Git tags；`topics` 独立存实际涉及的技术主题，不混用两种标签。

正文包含：

1. **范围与速览**：上游基线、本次同步版本、最值得关注的变化，完整的上游新增与删除列表；没有上游增量时说明原因。
2. **已跟踪变化与学习笔记**：按主题回答第 4 节的问题，结合相关 commit 说明关键代码路径、本地目标与采用差异；有实际影响的清单 diff 在对应主题中说明。
3. **值得引入**：清单外的少量候选，或明确写无。

写完重读报告并核对元数据、执行前清单 Git diff 结论、前序关系、新增与删除列表、主题覆盖及证据链接。确认上游历史变化、本次本地变化和清单变化没有混淆，建议没有被写成已完成的操作，再在对话中给出报告路径和少量关键收获。
